# 第一阶段填表清单：哪些必须有数据，哪些可以留空

日期：2026-10-09。按当前第一版[schema.sql](schema.sql)及[设计与评审.md](设计与评审.md)的18表启动范围细化。
逐表字段解释见[38张表逐一讲解.md](38张表逐一讲解.md)。
本文件是实施清单，不是要求用虚构数据填满数据库；不改变SQL要求。

## 1. 直接回答“第一阶段哪些表要填满？”

**不要求38表全满，也不要求18表的每一列全有值。**
第一阶段做到：纳入的真实研究有出处、有实验与情境、有观察结果、有正确实体和对应关系；
明确信息已经填好，未知信息明确保留，证据能回查原文。

原方案的18张启动表分成：

- **5张基础表**：compound、source_record、experiment、context、observation。
  首阶段研究集合应有这些基础记录；不是每一个实验都必须使用某化合物。
  对每项正式生物断言，source_record→experiment→observation证据链必须存在。
  context是项目首轮推荐必配的情境记录，**SQL仍允许observation.context_id为空**；
  宏观数据库来源未提供情境时可保留例外并标待核对，不能编造样本。
- **13张按内容填写的表**：`herb`、`taxon`、`host_target`、`disease`、`study_arm`、`exposure`、`reaction`、`reaction_participant`、`transformation`、`herb_compound`、`compound_target`、`compound_microbe`、`target_disease`。
  只有相应研究和证据才建记录；没有相应证据则零行是正常状态。
- **20张扩展表**：原方案主要留给机制深化，但不是禁止首轮使用。
  原文已经给出基因、酶、疾病终点或交叉喂养等结果，就提前启用相应表及依赖实体，
  不遗漏真实信息，也不把它们塞入语义不符的18张表中。

“填满”建议改成三个验收问题：
1. **身份够不够明确？** 能否区分化合物、菌分类级别、宿主物种、疾病体系？
2. **实验结果有没有依据？** 是否找到原文、方法、位置、处理和对照？
3. **缺口是否保留？** 未知菌/基因/酶没捏造，负结果与矛盾结果没覆盖。

## 2. 五张基础表怎样填写

| 表 | 首阶段至少做什么 | 允许未知什么 | 核查重点 |
|---|---|---|---|
| compound | 建纳入研究涉及的成分、底物、产物身份；name和identity_status明确 | inchikey可NULL；未解析身份可unresolved | 同名不同结构不能合并；未知结构不妨碍先保留名称 |
| source_record | kind、locator、version有实际出处或明确缺失约定；推荐补title/url | 未报道版本可按项目约定not_reported | 正式数据不用synthetic；综述引用同研究不重复计票 |
| experiment | 指向source_record；local_key区分实验；system明确 | 未报道宿主/模型/疾病可NULL，体系不明可unspecified | 菌群培养、酶实验、细胞/动物实验不混为一项 |
| context | 指向实验，记录method；尽量补site/timepoint/conditions | sample_accession等可NULL；条件未记录可{} | 实测与计算方法区分；method未报告须说明，保持待核对 |
| observation | 必填测量终点、指标、方向、方法、原文位置、抽取版本；人工核对状态 | 数值/p/q/组别可能NULL | NULL不等于0；accepted只是审核通过，不是已证实因果 |

对于数据库来源的注释：
system=computational只能在确有计算分析时使用；不能把所有来源均视为计算。
quote/location可记录原数据库文本及字段/记录定位，不能伪造论文引文。

## 3. 13张按研究内容填写的启动表

| 表 | 什么时候应该有行 | 没有证据时怎么办 |
|---|---|---|
| herb | 有明确药材来源、部位或炮制研究 | 只有纯化成分研究可空，不倒推药材来源 |
| taxon | 报道菌的分类身份、丰度或相关结果 | 只有菌群整体转化时可暂不造具体分类单元 |
| host_target | 报道具体宿主蛋白/复合物靶点 | 只有疾病终点或表达变化时不虚构靶点 |
| disease | 研究涉及疾病、疾病模型或关联 | 纯培养/纯化酶研究可不关联疾病 |
| study_arm | 有明确实验分组或比较对象 | 无实际组别的来源分析可空；不建立假的处理/对照 |
| exposure | 某实际组接受明确成分干预 | 不给对照组虚构成分A；剂量不明保留NULL |
| reaction | 有可支持的底物→产物过程 | 代谢物共现但来源未证明，不捏造反应 |
| reaction_participant | 已启用reaction并知道底物、产物角色 | 至少需要实际确认的底物和产物；未知共底物留待补 |
| transformation | 某实验报告该反应发生或未检出 | 无转化观察不造记录；未知催化者仍可录转化 |
| herb_compound | 有H含A的来源断言 | 无含成分证据不建立边 |
| compound_target | 有化合物作用具体宿主靶点的证据 | 只有表达变化时启用compound_host_gene |
| compound_microbe | 有成分处理后某菌的丰度/生长/存活结果 | 未报告菌变化可空；不把疾病分组差异塞进本表 |
| target_disease | 有靶点与疾病关系的独立来源支持 | 无依据让路径停在靶点，不能为凑闭环补一条边 |

阶段目标是能表达三条路径，不是每篇论文都得覆盖三条路径。
尤其路径③的“菌变化→功能变化→代谢变化”不能从丰度一项实验自动推导。

## 4. 首阶段每张启动表的SQL必填字段

下表不包括自动生成的id；有默认值字段可省略输入。
这是SQL下限，研究质控通常要求更多背景。可空字段完整清单见逐表文档。

| 表 | 非NULL字段（不含自动id） | 默认值 |
|---|---|---|
| `compound` | `name`、`identity_status` | 无 |
| `herb` | `name` | 无 |
| `taxon` | `name`、`rank` | 无 |
| `host_target` | `host_taxid`、`name`、`kind` | 无 |
| `disease` | `name`、`ontology`、`accession` | 无 |
| `source_record` | `kind`、`locator`、`version` | 无 |
| `experiment` | `source_id`、`local_key`、`system` | 无 |
| `study_arm` | `experiment_id`、`name`、`is_control` | 无 |
| `exposure` | `arm_id`、`compound_id` | 无 |
| `context` | `experiment_id`、`method`、`conditions` | `conditions`：'{}'::jsonb |
| `observation` | `experiment_id`、`endpoint`、`metric`、`direction`、`evidence_method`、`quote`、`location`、`review_status`、`extraction_version` | `review_status`：'pending' CHECK(review_status IN ('pending' |
| `reaction` | `name`、`direction`、`completeness` | 无 |
| `reaction_participant` | `reaction_id`、`compound_id`、`side`、`compartment` | `compartment`：'unknown' |
| `transformation` | `reaction_id`、`observation_id`、`substrate_origin`、`product_origin`、`attribution` | 无 |
| `herb_compound` | `herb_id`、`compound_id`、`observation_id`、`role` | 无 |
| `compound_target` | `compound_id`、`target_id`、`observation_id`、`action`、`route` | 无 |
| `compound_microbe` | `compound_id`、`taxon_id`、`observation_id`、`measurement` | 无 |
| `target_disease` | `target_id`、`disease_id`、`observation_id`、`relation` | 无 |

额外约束不能漏：
- exposure.dose和dose_unit同时有值或同时NULL。
- observation.subject_arm_id、control_arm_id、context_id若填写，必须属于相同experiment；
  subject与control不能是同组。
- p/q在0–1；未提供P值就NULL，不能补成0.05或0。
- reaction_participant四字段复合主键不得NULL；stoichiometry知道才填且>0。
- 要先有父记录再填写外键；文件里写实体名称，不等于数据库可以把名称直接填进bigint外键。
- source/功能库的缺失版本标记not_reported是项目约定，并非SQL默认或正式版本。
- 受控词中的unknown不等于无影响；direction=unchanged才是记录不变结果。
- “未知实体”不应创建一个名字unknown的通用化合物/菌/靶点让所有研究共用。

## 5. 哪些扩展表需要提前启用？

| 首轮文献出现的实际内容 | 提前使用的扩展表 | 依赖与注意事项 |
|---|---|---|
| 宿主基因表达变化 | host_gene、compound_host_gene | 用标准基因身份；不伪装成binds靶点关系 |
| 明确宿主基因—产物映射 | host_gene_product | 先有host_gene及host_target，且同物种 |
| 成分干预的实际疾病终点 | compound_disease | 先有compound/disease/observation；不把靶点关联当终点 |
| 疾病分组中的菌关联 | microbe_disease | 先有taxon/disease/observation；不是成分处理结果 |
| 明确转化参与分类菌 | transformation_actor | 若只知分类菌，可直接指taxon，不强建strain |
| 明确菌株与装配 | strain、genome | 先有taxon；没有正式装配标识时不能造genome |
| 具体基因编码具体蛋白 | microbial_gene、protein、gene_product | 必须有真实装配与位点；只知基因家族不足以建位点 |
| 具体酶催化反应 | protein、protein_reaction | 可先未知基因/菌株；保留纯化实验或计算方法 |
| KO/EC等功能注释 | functional_term、gene_annotation或protein_annotation | 有具体被注释对象才关联；预测/实验分开 |
| 明确基因簇及成员 | gene_cluster、cluster_member | 依赖具体装配及位点；不得跨装配 |
| 微生物具体基因表达变化 | compound_gene | 依赖microbial_gene及观察；DNA与RNA层级分开 |
| 微生物具体酶活或蛋白量变化 | compound_protein | 依赖protein及观察；数量与活性分开 |
| 供体→受体的交叉喂养 | cross_feeding | 必须确认两个菌及交换物；共同丰度变化不够 |

这里没有改变第一版的38表结构，只是明确“阶段划分不等于丢弃已有证据”。

## 6. 三条路径首轮各做一个什么样的案例？

| 路径 | 最小真实证据内容 | 主要写入表 | 允许缺口 |
|---|---|---|---|
| ①直接作用 | 明确成分和宿主靶点作用的观察；入血/肠道部位若不明用unknown | 基础五表；host_target、compound_target；有疾病关系再加disease/target_disease | 原型含药材、入血检出、疾病关系可能来自不同来源，不混成一项实验 |
| ②菌群转化 | 底物与产物转化有证据，能定位实验和检测方法 | compound、来源实验情境观察；reaction、reaction_participant、transformation | 催化菌、基因、酶可未知；没有靶点证据就暂时只到代谢物 |
| ③菌群扰动 | 明确干预与对照，某菌的丰度/生长等结果 | 基础五表；study_arm、exposure、taxon、compound_microbe | 未知功能/代谢段不从菌丰度自动补；有实际代谢/功能结果再扩展 |

建议先人工试录5–10篇原始研究，保证三路径至少各有一个可表达的案例；
这个数量是设计试录建议，不是科研统计样本量要求。
没有完整机制论文也可以启动，不要求每个案例连到疾病终点。

## 7. 实际填表顺序

1. 把文献/数据库出处写入source_record，并给原始研究设置明确定位。
2. 建compound及当次用到的herb、taxon、host_target、disease等身份。
3. 将来源分成独立experiment，不同实验体系分开。
4. 有组别就建study_arm，有成分干预就建exposure。
5. 建context，记录样本、时间和检测方法。
6. 逐个终点建observation，先pending，再人工核对；阴性/无变化也保留。
7. 按结果含义建相应关系；转化结果先建reaction及participant，再建transformation。
8. 已知参与者、基因、蛋白及注释时，按实际证据补相关扩展表。
9. 核对外键、字段语义、原文定位与重复研究，再置accepted。
10. 输出候选路径时返回每跳观察及来源，不自动新增“整体机制已证实”的边。

组别与干预的小例子：虚构研究“处理组用A、对照组用载体”，两组分别记录。
如果载体不是纳入化合物且当前结构不表达载体暴露，保存到context.conditions或待扩展导入说明，
不能给对照组建立一条接受A的exposure来“填满”。

## 8. 一份虚构记录怎样填写未知？

只为说明字段处理，以下不是可直接导入真实数据库的科研数据。

| 情形 | 正确记录 | 错误记录 |
|---|---|---|
| 只知道A名称，不知道结构 | compound.identity_status=unresolved；inchikey=NULL | 编造一个InChIKey |
| 已有A→B实验，未知催化菌 | transformation.attribution=community或unknown，依原文；actor零行 | 创建一个假菌株再写gene_id |
| 不知道产物是否药源性 | product_origin=unknown | 因给了A就写drug_derived |
| 菌相对丰度下降，P值未报 | measurement=relative_abundance；direction=decrease；p_value=NULL | promote/inhibit乱填，或补P=0 |
| 没有证据证明T和D相关 | 不建立target_disease | 为了图形闭环建立associated |
| 文献有反向结论 | 分别建立观察和关系行 | 用新结论覆盖旧行 |
| 无明确疾病标准ID | 暂留原始抽取待标准化 | 给正式disease编造ontology/accession |

待标准化记录是工作流程中另存的抽取表/文件，不是宣称现有schema已有一个staging表。
保留原文再审核，不必为了满足NOT NULL硬塞身份不明的关系。

## 9. 第一阶段验收清单

| 验收项 | 必须检查什么 |
|---|---|
| 表结构 | 已建表及外键按schema.sql运行；运行结果需在目标数据库实际验证 |
| 文献覆盖 | 能展示三条路径的案例，并说明各自知识缺口 |
| 来源闭环 | 每条关系或转化都有observation→experiment→source_record |
| 身份准确 | 化合物状态、菌分类级别、宿主物种和疾病标准均未捏造 |
| 组别与剂量 | 只在真实分组/干预存在时填，不把技术重复当受试者 |
| 方法与原文 | quote/location可核对；原文与中文解释区分；实测/预测区分 |
| NULL语义 | 未报道数值、统计量、结构和机制留空或用指定unknown |
| 结果完整 | 阳性、阴性、不变、矛盾均可保留，不覆盖已有观察 |
| 扩展证据 | 原文已有基因/酶/疾病终点就进入正确表，没有为了18表限制而丢失 |
| 路径查询 | 输出逐跳来源和条件；不同研究/物种的拼接标为候选机制 |

当前schema的外键不等于这些科研检查全部自动完成。
这一轮说明进行了38表、197字段的静态核对，没有再次执行数据库测试。

## 10. 给老师的汇报表述

“第一阶段不是把数据库填满，而是把少量原始研究录得完整、准确、能回查。
我们以18张表作为启动范围，五张基础表承载身份、来源、实验情境和观察，
其余按研究实际内容启用。未知机制保留缺口；已有基因、酶或疾病终点证据则提前使用扩展表。
之后围绕菌株—基因—蛋白—反应证据逐步深化。”
