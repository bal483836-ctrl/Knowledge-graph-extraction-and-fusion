## 先把“填满”说清楚

“有需要的表中有真实记录、每条记录的身份和证据链完整”，不等于把38张表都填非空。
一张表可有很多行，也可暂时零行；可空字段未知就保留NULL。
没有证据的关系应当**不创建关系行**，而不是创建一行全unknown的边来凑路径。
SQL必填、项目推荐、科学上能不能下结论，是三个不同层次。

所有例子H、A、B、X、S、G、L、E、T、J、D、R均为**虚构教学代号**，不得当作真实科研事实入库。
例子中外键写的是对象代号；正式数据库需改为已建立记录的内部id。
带IDENTITY的id由数据库自动生成；当前无单独id的复合主键表只有三张：cluster_member、host_gene_product、reaction_participant。
functional_term等的复合UNIQUE不是复合主键。

## 逐表解释

以下字段表中“必填”指建记录时SQL要求非NULL；对带默认值字段可以省略输入，但不可以随意传NULL。
“可空”不等于不重要，项目审核仍可能要求补查。

<a id="table-compound"></a>

### 1. compound：化合物

**一行是什么：**一种待区分的化学实体，而不是一次实验或一种角色。

**为什么要有这张表：**A在药材中是原型、在反应R中是底物；B在R中是产物、在另一反应中可成为底物，都使用同一compound表。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `name` | 必填 | 本表对象的名称，结合物种、来源或实体类型解释；名称通常不保证唯一。 |
| `inchikey` | 可空 | 用于核对精确化学结构的InChIKey；未知结构留NULL。 |
| `identity_status` | 必填 | 化合物身份解析状态：exact精确、partial部分解析、unresolved未解析。 |

**连接到哪里：**本表没有外键，其他关系表引用它的主键。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
inchikey varchar(27) UNIQUE
identity_status text NOT NULL CHECK (identity_status IN ('exact','partial','unresolved'))
```

**不要这样理解或填写：**InChIKey辅助精确结构匹配；名称不唯一，未知结构可入库。盐型、立体结构和未解析名称不能只凭名字合并。identity_status为exact/partial/unresolved，不表示疗效证据等级。

**第一阶段怎么处理：**首阶段核心实体；至少覆盖纳入研究涉及的干预物、底物及产物。

<a id="table-herb"></a>

### 2. herb：中药

**一行是什么：**一种明确来源描述的药材；药用部位和炮制也是身份核对的重要线索。

**为什么要有这张表：**虚构药材H报告含有A：H存herb，A存compound，两者的发现存herb_compound。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `name` | 必填 | 本表对象的名称，结合物种、来源或实体类型解释；名称通常不保证唯一。 |
| `medicinal_part` | 可空 | 药材的药用部位；未报告则留NULL。 |
| `processing` | 可空 | 炮制或加工描述；未报告则留NULL。 |

**连接到哪里：**本表没有外键，其他关系表引用它的主键。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

**不要这样理解或填写：**单独研究纯化成分且没有药材来源证据时，不反推H含A。现表name无唯一约束，导入时要避免同一药材重复。

**第一阶段怎么处理：**有药材来源时填写；研究对象只有纯化成分时可暂无记录。

<a id="table-taxon"></a>

### 3. taxon：微生物分类单元

**一行是什么：**一个属、种等分类单元，不能自动当成具体菌株。

**为什么要有这张表：**文献只写虚构菌属X，就按属级存name和rank；parent_id指向它的上级分类记录。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `name` | 必填 | 本表对象的名称，结合物种、来源或实体类型解释；名称通常不保证唯一。 |
| `rank` | 必填 | 微生物分类级别，按项目统一词表填写。 |
| `ncbi_taxid` | 可空 | 核对过的NCBI分类编号；不是本库taxon.id。 |
| `parent_id` | 可空 | 指向上级taxon.id的外键，可未知。 |

**连接到哪里：**`taxon(id)`。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
ncbi_taxid bigint UNIQUE
```

**不要这样理解或填写：**rank是自由文本，SQL未限定取值，项目统一词表。ncbi_taxid只在核对成功时填写；不能将未知分类写成一个假菌种。

**第一阶段怎么处理：**第一阶段菌丰度或分类关联所必需。

<a id="table-strain"></a>

### 4. strain：菌株或MAG归属

**一行是什么：**一个具体菌株或被追踪的MAG来源对象，其分类归属由taxon_id给出。

**为什么要有这张表：**X类菌的株S与同类株S2分别记录；若报告MAG，保留原始MAG身份，不能叫作已培养菌株。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `taxon_id` | 必填 | 指向taxon.id；其角色由本表含义决定。 |
| `name` | 必填 | 本表对象的名称，结合物种、来源或实体类型解释；名称通常不保证唯一。 |
| `accession` | 可空 | 对应对象的正式登录号；需结合本表解释所属库。 |

**连接到哪里：**`taxon(id)`。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
accession text UNIQUE
```

**不要这样理解或填写：**只到属/种分辨率时不造菌株。taxon_id必填；accession可空。

**第一阶段怎么处理：**通常第二阶段；已知菌株证据现在就应记录。

<a id="table-genome"></a>

### 5. genome：基因组装版本

**一行是什么：**某菌株或MAG的一次明确装配版本。

**为什么要有这张表：**S的assembly-v1和assembly-v2分开建记录，再把各版本的基因归到对应装配。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `strain_id` | 必填 | 指向strain.id；genome必须归属菌株，protein和转化参与者可未知。 |
| `assembly_version` | 必填 | 包含版本的装配标识；全库唯一。 |
| `completeness` | 可空 | 装配完整度，0–100百分比，未知NULL。 |
| `contamination` | 可空 | 装配污染度，0–100百分比，未知NULL。 |

**连接到哪里：**`strain(id)`。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
assembly_version text NOT NULL UNIQUE
completeness numeric CHECK (completeness BETWEEN 0 AND 100)
contamination numeric CHECK (contamination BETWEEN 0 AND 100)
```

**不要这样理解或填写：**assembly_version要求全库唯一，应保存带版本的正式标识；不能编造登录号。completeness/contamination是0–100百分比，未知留空。

**第一阶段怎么处理：**基因定位模块启用时填写，首阶段可以空。

<a id="table-microbial_gene"></a>

### 6. microbial_gene：具体微生物基因

**一行是什么：**某个具体基因组装配上的位点。

**为什么要有这张表：**装配G上的locus_L是一个基因；另一个装配上的同名L不是同一条记录。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `genome_id` | 必填 | 指向具体装配genome.id，不是菌种编号。 |
| `locus_tag` | 必填 | 该装配内具体基因位点的标识。 |
| `sequence_accession` | 可空 | 核对过的序列登录号，不明NULL。 |

**连接到哪里：**`genome(id)`。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
UNIQUE(genome_id,locus_tag)
```

**不要这样理解或填写：**genome_id+locus_tag唯一；genome_id不可空，所属装配不可通过更新改动。仅有KO编号、基因家族名而没有可定位身份时，不制造具体基因。

**第一阶段怎么处理：**第二阶段重点；一旦有确定位点和编码/调控证据立即启用。

<a id="table-gene_cluster"></a>

### 7. gene_cluster：基因簇

**一行是什么：**某装配内一个明确的多基因集合。

**为什么要有这张表：**G里的簇C作为集合建表，成员L1/L2分别通过cluster_member关联。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `genome_id` | 必填 | 指向具体装配genome.id，不是菌种编号。 |
| `name` | 必填 | 本表对象的名称，结合物种、来源或实体类型解释；名称通常不保证唯一。 |

**连接到哪里：**`genome(id)`。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
UNIQUE(id,genome_id)
```

**不要这样理解或填写：**不是单个基因；现表不存坐标和簇功能证据，不能只因成簇就判定共同催化。

**第一阶段怎么处理：**有簇级研究时启用，首阶段可空。

<a id="table-cluster_member"></a>

### 8. cluster_member：基因簇成员

**一行是什么：**某基因属于某簇的一对身份关系。

**为什么要有这张表：**(C,L1)、(C,L2)两行，而不是把多个基因名塞进一格。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `cluster_id` | 必填 | 指向gene_cluster.id。 |
| `gene_id` | 必填 | 本表连接的基因内部编号；微生物关系指microbial_gene，宿主关系指host_gene。 |

**连接到哪里：**`gene_cluster(id)`、`microbial_gene(id)`。

**关键约束（SQL原文摘录）：**

```sql
PRIMARY KEY(cluster_id,gene_id)
```

**不要这样理解或填写：**复合主键(cluster_id,gene_id)，不自动生成id。触发器要求簇和基因同装配；本表没有observation_id。成员归属来源需在导入记录中保留。

**第一阶段怎么处理：**与基因簇一同启用，未知成员不填。

<a id="table-protein"></a>

### 9. protein：具体微生物蛋白或酶

**一行是什么：**一个具有可区分身份的微生物蛋白；是否催化特定底物通过关系证据表达。

**为什么要有这张表：**蛋白E在纯化实验中催化A→B：E存protein，催化关系存protein_reaction。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `name` | 必填 | 本表对象的名称，结合物种、来源或实体类型解释；名称通常不保证唯一。 |
| `uniprot_accession` | 可空 | 核对过的具体蛋白UniProt登录号，可空。 |
| `sequence_accession` | 可空 | 核对过的序列登录号，不明NULL。 |
| `strain_id` | 可空 | 指向strain.id；genome必须归属菌株，protein和转化参与者可未知。 |

**连接到哪里：**`strain(id)`。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
uniprot_accession text UNIQUE
```

**不要这样理解或填写：**EC是功能类别，不能当具体蛋白身份。uniprot_accession和sequence_accession可空；但泛称某酶家族不能伪装为单个确定蛋白。未知株时strain_id可空。

**第一阶段怎么处理：**第二阶段重点；首轮有纯化酶研究就启用。

<a id="table-functional_term"></a>

### 10. functional_term：功能类别

**一行是什么：**某功能库某版本下的一项分类标签。

**为什么要有这张表：**namespace=KO/EC/Pfam/CAZy，accession填核对过的类别编号，release填实际数据库版本。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `namespace` | 必填 | 功能类别所属库，如KO、EC、Pfam、CAZy；统一命名。 |
| `accession` | 必填 | 对应对象的正式登录号；需结合本表解释所属库。 |
| `release` | 必填 | 功能库实际版本；缺失按明确项目约定记录，不能编造版本。 |
| `name` | 可空 | 本表对象的名称，结合物种、来源或实体类型解释；名称通常不保证唯一。 |

**连接到哪里：**本表没有外键，其他关系表引用它的主键。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
UNIQUE(namespace,accession,release)
```

<a id="table-observation"></a>

### 20. observation：具体观察证据

**一行是什么：**某实验情境下的一项可定位的测量结果或来源断言。

**为什么要有这张表：**A组某菌相对丰度下降，另一个时间点不变，建不同观察，而非改掉旧行。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `experiment_id` | 必填 | 指向所属experiment.id。 |
| `context_id` | 可空 | 指向与该观察同实验的context。 |
| `subject_arm_id` | 可空 | 处理/受试组编号，须属于该观察实验。 |
| `control_arm_id` | 可空 | 比较对照组编号，须属于该观察实验且不能与受试组相同。 |
| `endpoint` | 必填 | 到底测什么，如X菌相对丰度、T靶点活性、某疾病评分。 |
| `metric` | 必填 | 用什么指标量化，如relative_abundance、log2FC、activity、presence。 |
| `direction` | 必填 | observation为increase/decrease/unchanged/detected/not_detected/unknown；reaction为forward/reversible/unknown。 |
| `value` | 可空 | 原文报告的数值；须与metric、unit共同解释。 |
| `unit` | 可空 | 数值单位；无量纲指标需明示dimensionless或按项目词表说明。 |
| `p_value` | 可空 | 原文P值，0–1；未报告NULL。 |
| `q_value` | 可空 | 原文校正后的Q值，0–1；不能自行将P复制成Q。 |
| `evidence_method` | 必填 | 支持该观察的实验/计算/注释方式，区别预测与实测。 |
| `quote` | 必填 | 准确原文摘录；中文解释不可冒充原文。 |
| `location` | 必填 | 原文定位，如结果段、表号、图号或数据库字段。 |
| `review_status` | 必填；有默认值 | pending待核对、accepted审核通过、rejected不纳入；非科学证据等级。 |
| `extraction_version` | 必填 | 人工规则或抽取工具版本，用于追踪修改。 |

**连接到哪里：**`experiment(id)`、`context(id,experiment_id)`、`study_arm(id,experiment_id)`。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
direction text NOT NULL CHECK(direction IN ('increase','decrease','unchanged','detected','not_detected','unknown'))
p_value numeric CHECK(p_value BETWEEN 0 AND 1)
q_value numeric CHECK(q_value BETWEEN 0 AND 1)
review_status text NOT NULL DEFAULT 'pending' CHECK(review_status IN ('pending','accepted','rejected'))
FOREIGN KEY(context_id,experiment_id) REFERENCES context(id,experiment_id)
FOREIGN KEY(subject_arm_id,experiment_id) REFERENCES study_arm(id,experiment_id)
FOREIGN KEY(control_arm_id,experiment_id) REFERENCES study_arm(id,experiment_id)
CHECK(subject_arm_id IS NULL OR control_arm_id IS NULL OR subject_arm_id<>control_arm_id)
```

**不要这样理解或填写：**endpoint=测什么，metric=用什么指标，direction=结果方向；quote/location必须能定位原文。p/q未知NULL，不写0；review_status=accepted只表示审核通过，不表示因果成立。

**第一阶段怎么处理：**所有生物作用/注释断言的证据入口，第一阶段最关键。

| `gene_id` | 必填 | 本表连接的基因内部编号；微生物关系指microbial_gene，宿主关系指host_gene。 |
| `observation_id` | 必填 | 指向支持本条断言或转化的observation.id。 |
| `level` | 必填 | compound_gene为dna_abundance/rna_expression/unknown；compound_protein为protein_abundance/enzyme_activity/unknown。 |

**连接到哪里：**`compound(id)`、`microbial_gene(id)`、`observation(id)`。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
level text NOT NULL CHECK(level IN ('dna_abundance','rna_expression','unknown'))
```

**不要这样理解或填写：**level=dna_abundance/rna_expression/unknown；RNA变化不能推出蛋白活性。只有家族层丰度且无法定位具体基因时，不捏造microbial_gene。

**第一阶段怎么处理：**功能变化研究可首轮启用，否则待后续。

| `observation_id` | 必填 | 指向支持本条断言或转化的observation.id。 |

**连接到哪里：**`compound(id)`、`protein(id)`、`observation(id)`。

**不要这样理解或填写：**蛋白量与酶活不同；本表不是成分—宿主靶点表。只报告酶家族总体活性而无具体蛋白时先保留待解析记录。

<a id="table-cross_feeding"></a>

### 37. cross_feeding：菌间交叉喂养

**一行是什么：**供体菌给受体菌提供明确交换物的一条证据断言。

**为什么要有这张表：**X向Y提供B，donor_id=X、recipient_id=Y、compound_id=B。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `donor_id` | 必填 | 供体菌的taxon.id，交叉喂养方向起点。 |
| `recipient_id` | 必填 | 受体菌的taxon.id，交叉喂养方向终点。 |
| `compound_id` | 必填 | 指向compound.id，作用物、底物、产物或交换物由本表角色指定。 |

**不要这样理解或填写：**供受体不能相同；两个分类外键表达方向。共同升高不构成交叉喂养证据；交换物未知时不能虚构B以满足NOT NULL。

### 38. compound_disease：成分干预疾病结局

**一行是什么：**某成分与某疾病终点改善、恶化、不变或关联的一条断言。

**为什么要有这张表：**A干预后D的一个实际终点改善，relation=improved，endpoint具体写终点。

**所有字段怎么填：**

| 字段 | SQL填写要求 | 大白话含义 |
|---|---|---|
| `id` | 自动生成，通常不手填 | 本库内部记录编号，由数据库自动生成；不是外部数据库登录号。 |
| `compound_id` | 必填 | 指向compound.id，作用物、底物、产物或交换物由本表角色指定。 |
| `disease_id` | 必填 | 指向disease.id；experiment可不涉及疾病。 |
| `observation_id` | 必填 | 指向支持本条断言或转化的observation.id。 |
| `relation` | 必填 | 本关系的生物学类别，取值范围取决于该表CHECK，见约束摘录。 |

**连接到哪里：**`compound(id)`、`disease(id)`、`observation(id)`。

**关键约束（SQL原文摘录）：**

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY

```

**不要这样理解或填写：**不用target_disease推导生成。不同终点可相反，分别保存；clinical相关与干预疗效不能混写。

**第一阶段怎么处理：**凡第一阶段已纳入疾病终点研究，就必须启用此表记录，不能等第三阶段才丢回补。

## 不同层次的表，不能互相替代

| 容易混淆的一对 | 区别 |
|---|---|
| taxon / strain | 菌的分类单元与具体菌株不同 |
| genome / microbial_gene | 装配版本与其中的具体位点不同 |
| microbial_gene / functional_term | 具体基因身份与功能分类不同 |
| gene_product / protein_reaction | 编码蛋白与催化特定反应不同 |
| reaction / transformation | 反应定义与一次研究中的转化观察不同 |
| protein_annotation / protein_reaction | 分到某功能类别不等于证实对特定底物的催化 |
| compound_host_gene / compound_target | 宿主表达变化不等于蛋白直接结合 |
| compound_microbe / microbe_disease | 成分处理后的菌变化与疾病分组中的菌关联不同 |
| target_disease / compound_disease | 靶点与疾病关系不等于某成分实际改变疾病终点 |
| source_record / experiment / observation | 来源、独立实验、具体结果三个粒度不同 |

## 现有第一版结构的边界

- 没有实体别名、实体变更审计、复方暴露、复合酶亚基、动力学参数专表；不能在文档中假装这些已存在。
- 默认JSON conditions可保存实际报告的补充条件，但不是随意扩展关系类型的替代。
- herb、taxon、protein等身份的某些字段允许缺失，导入审核仍须确认未错误合并。
- gene_product有证据入口，但没有assignment；用observation详细记录编码证据方法。
- cluster_member及host_gene_product是身份映射表，没有observation_id，当前表内无法逐行连接来源；
  首轮若使用，需在导入日志中记录来源，后续可扩展映射证据表，不凭空增加不存在的列。
- 值域约束与外键只能检查结构；不能证明生物关系、化学平衡、蛋白归属或整条因果链。
- 这份文档为按现SQL逐项核对的说明；没有再次运行PostgreSQL建库，不把说明审核当数据库运行验收。
